# Обоснование выбранного AI-подхода и преимущества системы

Данный документ описывает преимущества выбранного подхода к построению системы анализа новостного фона, обработки событий и формирования аналитических ответов. Основной акцент сделан не на структуре файлов и сервисов, а на том, почему используются именно такие технологии и почему их сочетание подходит для задачи финансово-новостной аналитики.

## 1. Особенность решаемой задачи

Финансовые новости являются неструктурированным источником данных. В отличие от котировок, таблиц или бухгалтерских показателей, новостной поток состоит из текстов разного качества, длины, языка, стилистики и степени достоверности. Один и тот же факт может быть описан десятками источников с разными формулировками:

```text
ЦБ повысил ключевую ставку
Банк России ужесточил денежно-кредитную политику
Регулятор поднял ставку из-за инфляционных рисков
```

Для человека эти сообщения близки по смыслу. Для обычного поиска по ключевым словам они могут выглядеть как разные тексты. Поэтому система должна уметь работать не только со словами, но и со смыслом.

В проекте решается несколько связанных задач:

- сбор и нормализация большого новостного потока;
- удаление дублей и технического шума;
- смысловая группировка новостей в события;
- извлечение сущностей: компаний, стран, валют, регуляторов, отраслей и макроэкономических понятий;
- оценка связи события с активами;
- построение базы знаний для вопросно-ответного режима;
- формирование объяснимой аналитической сводки.

Такой класс задач плохо решается одним алгоритмом. Поэтому используется комбинированный подход: классические алгоритмы отвечают за детерминированные операции, а языковые модели применяются там, где требуется смысловая интерпретация.

## 2. Почему используется гибридный подход

В системе сознательно не используется подход, при котором вся логика передаётся одной LLM. Это важно по нескольким причинам.

Во-первых, языковая модель хорошо понимает смысл текста, но не является надёжным источником фактов сама по себе. Она может обобщать, объяснять и классифицировать, но не должна самостоятельно “вспоминать” новости, цены или события без проверяемого контекста.

Во-вторых, финансовая аналитика требует воспроизводимости. Если событие было отнесено к определённому активу, должна быть возможность понять, на основании каких новостей и признаков это произошло.

В-третьих, часть задач должна решаться строго алгоритмически:

- дедупликация по URL и тексту;
- чтение больших CSV-файлов;
- построение embedding-векторов;
- поиск ближайших документов;
- расчёт рыночной дельты;
- расчёт impact;
- сохранение индексов и результатов;
- контроль лимитов, таймаутов и размера контекста.

Поэтому архитектура следует принципу:

```text
алгоритмы считают и проверяют;
LLM интерпретирует и объясняет;
RAG ограничивает ответ найденными фактами.
```

Такой подход снижает риск галлюцинаций и делает результат более пригодным для аналитического использования.

## 3. Роль искусственного интеллекта в системе

ИИ используется не как “чёрный ящик”, который принимает решение за пользователя, а как инструмент смысловой обработки текста.

В системе языковые модели применяются для следующих задач:

- классификация типа события;
- определение смысловой связи события с активом;
- генерация альтернативных поисковых запросов для повышения полноты retrieval;
- формирование объяснения для пользователя;
- создание рыночной сводки на основе найденного контекста;
- диалоговый режим поверх базы знаний.

При этом модель не заменяет рыночные данные и не рассчитывает численные показатели “по мнению”. Например, влияние события на актив вычисляется кодом на основе рыночной дельты и веса релевантности:

```text
impact = price_delta * relevance_weight
```

Такое разделение повышает надёжность: LLM объясняет экономический смысл, но не подменяет фактические расчёты.

## 4. Почему используется RAG

RAG, или Retrieval-Augmented Generation, выбран потому, что обычная LLM не знает актуальных локальных данных проекта. Даже если модель обладает общими знаниями об экономике, она не имеет доступа к свежим новостям, результатам парсинга, обработанным событиям и аналитическим файлам системы.

RAG решает эту проблему следующим образом:

```text
вопрос пользователя
    ↓
поиск релевантных документов в индексе
    ↓
формирование контекста
    ↓
передача контекста в LLM
    ↓
ответ на основе найденных данных
```

Преимущество RAG в том, что модель отвечает не “из памяти”, а на основе актуальной базы знаний, собранной системой.

Для данного проекта это особенно важно, потому что новостной фон быстро меняется. Модель не нужно постоянно дообучать в классическом смысле. Достаточно обновлять индекс новостей и событий. Это быстрее, дешевле и прозрачнее.

## 5. Почему не используется только fine-tuning

Fine-tuning полезен, когда нужно изменить стиль поведения модели, обучить её специфическому формату ответа или закрепить типовые паттерны. Однако для задачи актуальной новостной аналитики он не является основным механизмом.

Причины:

- новости быстро устаревают;
- дообучение требует времени и вычислительных ресурсов;
- fine-tuning не гарантирует точное воспроизведение конкретных фактов;
- после дообучения сложно проверить, из какого источника модель взяла утверждение;
- модель может смешивать старые и новые сведения.

В проекте более уместна RAG-архитектура: данные остаются во внешней базе знаний, а LLM получает их как контекст во время запроса. Это делает систему более управляемой.

Иными словами:

```text
fine-tuning меняет модель;
RAG обновляет знания вокруг модели.
```

Для новостей второй вариант практичнее, потому что позволяет быстро добавлять свежие данные без переобучения всей модели.

## 6. Почему используется chunking

Новостные статьи и аналитические документы могут быть длинными. Если передавать их в модель целиком, возникают проблемы:

- превышается лимит контекста;
- embedding длинного текста становится менее точным;
- поиск может вернуть весь документ, хотя нужен один абзац;
- увеличивается стоимость и время обработки;
- в ответ попадает лишний шум.

Поэтому тексты делятся на чанки — небольшие фрагменты фиксированного размера с overlap. Overlap нужен для сохранения смысла на границах фрагментов.

Пример:

```text
chunk 1: слова 0-180
chunk 2: слова 140-320
chunk 3: слова 280-460
```

Такой подход повышает точность поиска. Система может найти не всю статью, а конкретный фрагмент, где говорится об инфляции, ставке, нефти, санкциях или конкретной компании.

## 7. Почему используются embeddings

Embedding — это числовое представление смысла текста. Оно позволяет сравнивать документы не только по совпадению слов, но и по смысловой близости.

Например, запрос:

```text
Что происходит с ростом цен?
```

может найти документы, где используются слова:

```text
инфляция
потребительские цены
индекс цен
удорожание
```

Классический keyword-поиск может пропустить такие связи, если слова не совпали. Embedding-поиск решает эту проблему.

В проекте embeddings используются в двух направлениях:

- в EDMI для смысловой обработки новостей и событий;
- в RAGPipe для построения поисковой базы знаний.

Для RAGPipe используется embedding-модель Ollama `nomic-embed-text`. Она позволяет локально строить векторные представления документов и запросов без отправки данных во внешние сервисы.

## 8. Почему используется FAISS

FAISS используется для быстрого поиска ближайших embedding-векторов. После того как каждый chunk превращён в вектор, нужно уметь быстро находить наиболее похожие документы.

Без специализированного индекса поиск по большому количеству векторов был бы медленным. FAISS оптимизирован именно для similarity search и позволяет эффективно находить ближайшие документы в многомерном пространстве.

В проекте FAISS выполняет роль семантического поискового слоя:

```text
вопрос пользователя
    ↓
embedding вопроса
    ↓
поиск ближайших chunk-векторов
    ↓
релевантные документы
```

Это особенно полезно в финансовых новостях, где важны не только прямые совпадения слов, но и смысловые связи.

## 9. Почему используется BM25

BM25 — это классический алгоритм ранжирования документов по ключевым словам. Он хорошо работает, когда в запросе есть точные термины:

- название компании;
- тикер;
- фамилия политика;
- название регулятора;
- страна;
- валюта;
- конкретный показатель.

Например, если пользователь спрашивает про `Росстат`, `Brent`, `ФРС`, `SBER` или `ключевую ставку`, BM25 помогает найти документы с точными совпадениями.

Embedding-поиск и BM25 дополняют друг друга:

```text
FAISS ищет по смыслу;
BM25 ищет по словам;
hybrid retrieval объединяет оба подхода.
```

Это повышает устойчивость поиска. Если semantic search ошибся, keyword-поиск может вернуть точный документ. Если keyword-поиск не нашёл совпадение, semantic search может найти близкий по смыслу материал.

## 10. Почему используется Chroma

Chroma используется как дополнительный persistent vector store. Он хранит документы и embeddings в удобном для retrieval формате и дополняет FAISS.

Преимущество Chroma в том, что это не просто файл индекса, а отдельное хранилище, удобное для расширения системы:

- можно хранить документы с метаданными;
- можно выполнять vector retrieval;
- можно развивать коллекции по типам данных;
- можно использовать persistent-хранилище между запусками.

В текущей системе Chroma работает как дополнительный retrieval-слой, повышающий гибкость RAGPipe.

## 11. Почему используется hybrid retrieval

Один способ поиска редко даёт стабильный результат на всех типах вопросов. Поэтому используется hybrid retrieval, объединяющий несколько источников релевантности:

- BM25 score;
- FAISS similarity;
- Chroma vector search;
- keyword score;
- recency boost;
- domain-specific boost;
- фильтрация шумовых документов.

Такой подход полезен для финансовых новостей, потому что пользовательские вопросы бывают разными.

Пример точного вопроса:

```text
Что известно по Росстату и инфляции?
```

Здесь важны ключевые слова.

Пример смыслового вопроса:

```text
Какие события могут давить на рынок?
```

Здесь важен semantic search.

Пример аналитического вопроса:

```text
Какие макроэкономические риски сейчас наиболее заметны?
```

Здесь нужны и смысловая близость, и свежесть, и экономические маркеры.

Hybrid retrieval позволяет обрабатывать все эти типы запросов в единой системе.

## 12. Почему используется multi-query retrieval

Пользовательский вопрос может быть коротким или неполным. Например:

```text
Что по рынку?
```

Для поиска в базе знаний такой запрос слишком общий. Multi-query retrieval решает эту проблему: LLM генерирует несколько альтернативных поисковых формулировок, которые раскрывают возможный смысл вопроса.

Пример:

```text
Что по рынку?
рыночная сводка экономика инфляция ставки нефть газ санкции геополитика
market brief macro economy rates inflation oil gas geopolitics
```

Важно, что эти дополнительные запросы не считаются фактами. Они используются только для повышения полноты поиска. В ответ пользователю должны попадать только сведения из найденных документов.

Преимущество multi-query подхода — повышение recall, то есть вероятности найти релевантные документы даже при коротком или неточном вопросе.

## 13. Почему используется rerank layer

Первичный поиск может вернуть много кандидатов. Среди них могут быть документы, которые частично совпали по словам или общей теме, но не являются лучшими для ответа.

Rerank layer переоценивает найденные документы относительно исходного вопроса. Это позволяет улучшить порядок результатов и передать в LLM более качественный контекст.

В проекте rerank сделан как отдельный слой, который можно включать или отключать настройкой. Это важно, потому что reranking повышает качество, но может замедлять ответ и требовать дополнительных ресурсов.

Такой подход даёт баланс между скоростью и точностью.

## 14. Почему используется память

Memory store сохраняет историю выбранных документов, событий и ответов. Это полезно не как источник абсолютной истины, а как дополнительный контекст.

Память позволяет:

- учитывать ранее обработанные данные;
- сохранять историю диалога;
- поддерживать более связный аналитический контекст;
- использовать результаты прошлых запусков.

При этом память не должна заменять retrieval по свежему индексу. Она является вспомогательным слоем.

## 15. Почему используется локальная Ollama

Ollama выбрана для локального запуска LLM и embedding-моделей. Это даёт несколько преимуществ.

Первое преимущество — автономность. Система может работать локально без обязательной зависимости от внешнего API.

Второе преимущество — контроль данных. Новостные данные, пользовательские вопросы и аналитические результаты не отправляются во внешние облачные сервисы.

Третье преимущество — воспроизводимость окружения. Модель можно зафиксировать, например:

```text
llama3.1
nomic-embed-text
```

Четвёртое преимущество — удобство интеграции. Ollama предоставляет HTTP API, через который можно строить embeddings, запускать генерацию и streaming-ответы.

Для дипломного проекта это важно, потому что система демонстрирует полноценный локальный AI-пайплайн:

```text
локальные данные → локальные embeddings → локальный retrieval → локальная LLM
```

## 16. Почему используется потоковая выдача ответа

Streaming нужен для улучшения пользовательского опыта. Если ответ генерируется несколько секунд, пользователь не должен смотреть на пустой экран.

При streaming модель отдаёт ответ частями:

```text
фрагмент 1 → фрагмент 2 → фрагмент 3 → ...
```

Это делает чат более удобным и визуально быстрым. Особенно это важно для аналитических ответов, где модель может формировать несколько абзацев.

Streaming не меняет качество аналитики, но делает интерфейс пригодным для реального использования.

## 17. Почему используется отдельный парсер новостей

Сбор новостей вынесен в отдельный компонент, потому что это отдельная по природе задача.

Парсер отвечает за:

- обход источников;
- загрузку страниц;
- обработку сетевых ошибок;
- retry при временных сбоях;
- нормализацию текстов;
- сохранение CSV.

EDMI и RAGPipe не должны заниматься сетевым обходом сайтов. Их задача — анализировать уже собранные данные.

Такое разделение повышает надёжность и упрощает развитие системы. Можно менять список источников, стратегию retry или правила парсинга без изменения логики аналитики.

## 18. Почему данные проходят два параллельных пути

В системе предусмотрены два связанных, но разных направления обработки.

Первое направление — RAGPipe:

```text
сырые новости
    ↓
chunking
    ↓
embeddings
    ↓
FAISS + BM25 + Chroma + Memory
    ↓
чат и поиск по базе знаний
```

Это направление нужно для быстрого вопросно-ответного доступа к новостям.

Второе направление — EDMI processing:

```text
новости
    ↓
очистка и дедупликация
    ↓
NER
    ↓
агрегация в события
    ↓
классификация
    ↓
связь с активами
    ↓
аналитические файлы
```

Это направление нужно для структурированной аналитики по событиям и активам.

Затем результаты EDMI также попадают в RAGPipe. Благодаря этому чат знает не только сырые новости, но и уже обработанные события, сводки и выводы.

Итоговая база знаний содержит два уровня:

```text
фактический уровень: сырые новости;
аналитический уровень: события, активы, сводки, объяснения.
```

Это сильнее, чем использовать только один источник данных.

## 19. Почему используется CSV как промежуточный формат

CSV выбран как простой и прозрачный формат обмена между парсером, EDMI и RAGPipe.

Преимущества CSV:

- легко проверить вручную;
- можно открыть в таблицах;
- удобно использовать в batch-пайплайне;
- не требует сложной инфраструктуры на первом этапе;
- хорошо подходит для воспроизводимых экспериментов.

При этом система читает CSV потоково, а не загружает весь файл целиком в память. Это важно для масштабирования: объём новостей может расти, и обработка не должна зависеть от размера файла как от ограничения оперативной памяти.

## 20. Почему важна дедупликация

Новостной фон содержит множество повторов. Один и тот же материал может:

- перепечатываться разными источниками;
- появляться в RSS несколько раз;
- обновляться с тем же URL;
- повторяться в разных формулировках.

Если не выполнять дедупликацию, система будет переоценивать значимость повторяющихся событий. Например, одно событие, опубликованное двадцатью источниками, может быть ошибочно воспринято как двадцать независимых событий.

Поэтому дедупликация нужна не только для экономии ресурсов, но и для корректной аналитики. Она снижает информационное смещение и делает сводку более устойчивой.

## 21. Почему используется NER

NER, или named entity recognition, нужен для извлечения экономически значимых объектов из текста.

Сырые новости содержат обычный текст. Для аналитики важно выделить:

- компании;
- страны;
- валюты;
- регуляторов;
- персон;
- отрасли;
- товары;
- макроэкономические понятия.

NER превращает текст в набор сущностей, которые можно использовать в последующей логике.

Например:

```text
ФРС сохранила ставку, а цены на нефть Brent выросли
```

можно преобразовать в признаки:

```text
регулятор: ФРС
макроэкономический показатель: ставка
сырьевой товар: Brent
событие: изменение цен на нефть
```

Для русского языка используется Natasha, потому что она хорошо подходит для русскоязычного NER и морфологической обработки.

## 22. Почему LLM не должна считать финансовый результат самостоятельно

В финансовых задачах важно разделять интерпретацию и измерение.

LLM может объяснить, почему событие потенциально важно:

```text
рост ставки повышает стоимость капитала
```

Но численную реакцию рынка следует рассчитывать по данным:

```text
price_before
price_after
delta
impact
```

Если поручить LLM “оценить влияние” без рыночных данных, результат будет субъективным. Поэтому в системе LLM не является источником численной истины. Она формирует объяснение уже после того, как код рассчитал показатели.

Это делает систему более научно корректной:

```text
модель объясняет;
данные измеряют.
```

## 23. Почему используется вес релевантности события к активу

Не каждое событие одинаково влияет на каждый актив. Например, изменение ключевой ставки может напрямую влиять на банки, косвенно — на девелоперов, и почти не влиять на отдельную экспортную компанию.

Поэтому связь события с активом задаётся уровнями:

```text
direct
industry
supply_chain
macro
global
noise
```

Каждый уровень получает вес. Это позволяет различать прямое и косвенное влияние.

Пример:

```text
direct = 1.0
industry = 0.7
supply_chain = 0.5
macro = 0.3
global = 0.2
noise = 0.0
```

Такой подход делает расчёт impact более аккуратным. Одно и то же событие может быть важным для одного актива и почти нерелевантным для другого.

## 24. Почему важно хранить источники и метаданные

Каждый документ в индексе хранит не только текст, но и метаданные:

- заголовок;
- источник;
- URL;
- дату публикации;
- дату загрузки;
- идентификатор chunk;
- связь с исходной строкой CSV.

Это нужно для проверяемости. Пользователь или исследователь может понять, откуда взялась информация в ответе.

Для аналитической системы это критично: ответ без источника сложнее проверять и защищать. Наличие метаданных повышает доверие к результату.

## 25. Почему важна фильтрация шума

Новостные источники могут содержать материалы, не относящиеся к рынку:

- спорт;
- кино;
- справочные страницы;
- рекламные блоки;
- технические тексты;
- навигационные элементы.

Если такие документы попадут в RAG, они могут ухудшить ответы. Поэтому система использует фильтрацию шума и доменные признаки.

Например, документы с маркерами вроде `спорт`, `фильм`, `справочник` получают понижение или исключаются из выдачи. А документы с маркерами `инфляция`, `ставка`, `нефть`, `газ`, `санкции`, `ЦБ`, `ФРС` получают дополнительный вес.

Это не заменяет семантический поиск, но помогает направить retrieval в сторону финансово значимых материалов.

## 26. Почему важна свежесть данных

В финансовой аналитике время имеет большое значение. Новость за сегодняшний день обычно важнее новости годичной давности, если пользователь спрашивает о текущем фоне.

Поэтому retrieval учитывает дату публикации. Более свежие документы получают дополнительный вес, а слишком старые материалы могут понижаться.

Это особенно важно для вопросов вида:

```text
Что сейчас происходит на рынке?
Какие последние новости?
Какие события сегодня важны?
```

Такой механизм делает ответы ближе к актуальному состоянию базы знаний.

## 27. Почему система масштабируется на большое количество активов

В системе не предполагается, что список активов фиксирован. Активов может быть много, поэтому логика должна быть масштабируемой.

Для этого используется событийный подход:

```text
сначала выделяются события;
затем события сопоставляются с активами.
```

Это лучше, чем анализировать каждую новость отдельно для каждого актива. Если активов много, прямой перебор “каждая новость × каждый актив” быстро становится дорогим.

Агрегация новостей в события снижает объём работы:

```text
1000 новостей → 120 событий → сопоставление событий с активами
```

Такой подход экономит вычисления и уменьшает количество повторяющихся объяснений.

## 28. Почему используется монолитная интеграция в Tradematic

Изначально компоненты могли существовать отдельно: парсер, EDMI, RAGPipe, UI. Однако для пользовательского сценария они должны работать как единая система.

Интеграция в Tradematic даёт следующие преимущества:

- единая точка запуска;
- общий набор зависимостей;
- единый каталог данных;
- единый Docker Compose;
- единый UI;
- общий индекс базы знаний;
- единая авторизация для доступа к чату.

Это уменьшает операционную сложность. Пользователю не нужно вручную запускать несколько независимых проектов и следить, чтобы они использовали одни и те же файлы.

## 29. Почему чат доступен после авторизации

Чат работает с новостной и аналитической базой знаний, которая может содержать пользовательский контекст, портфельные активы, историю запросов и результаты обработки.

Поэтому доступ к нему должен быть защищён. Размещение кнопки чата после авторизации соответствует базовому принципу:

```text
аналитический функционал доступен только пользователю внутри системы.
```

Это также предотвращает случайное использование API чата внешними пользователями без сессии.

## 30. Почему используется Docker Compose

Docker Compose нужен для воспроизводимого запуска всех сервисов.

Система включает несколько компонентов:

- Django-приложение Tradematic;
- EDMI API;
- парсер новостей;
- RAGPipe;
- Ollama;
- Open WebUI;
- Redis;
- PostgreSQL;
- фоновые pipeline-задачи.

Ручной запуск всех компонентов повышает вероятность ошибок. Docker Compose фиксирует окружение, сетевые адреса, volumes и зависимости между сервисами.

Это важно для демонстрации и эксплуатации: проект можно поднять одной командой в предсказуемом состоянии.

## 31. Почему используется локальное хранение индекса

RAGPipe сохраняет индекс в каталоге:

```text
main/scripts/datasets/ragpipe/
```

Там хранятся:

- документы и чанки;
- BM25 индекс;
- FAISS индекс;
- Chroma база;
- memory;
- метаданные.

Локальное хранение удобно для отладки и воспроизводимости. После построения индекса его можно использовать повторно без полного пересчёта. Это ускоряет тестирование чата и снижает нагрузку на embedding-модель.

## 32. Преимущества выбранной архитектуры

Ключевые преимущества системы:

1. **Актуальность**  
   База знаний обновляется из свежих новостей, а не ограничивается знаниями модели на момент обучения.

2. **Проверяемость**  
   Ответы строятся на найденных документах с источниками, датами и URL.

3. **Снижение галлюцинаций**  
   LLM получает ограниченный RAG-контекст и не должна выдумывать факты вне него.

4. **Гибкость**  
   Можно менять источники новостей, модели embeddings, LLM, лимиты контекста и параметры retrieval.

5. **Масштабируемость**  
   Система обрабатывает данные потоково, строит индексы и работает с чанками, а не с огромными текстами целиком.

6. **Локальность**  
   Ollama позволяет запускать LLM и embeddings локально.

7. **Комбинирование методов**  
   Используются и классические алгоритмы, и современные языковые модели.

8. **Объяснимость**  
   Пользователь получает не только результат, но и текстовое объяснение причин.

9. **Разделение ответственности**  
   Парсер собирает данные, EDMI структурирует события, RAGPipe отвечает за поиск и чат, UI отображает результат.

10. **Пригодность для развития**  
    Архитектура позволяет добавлять новые источники, модели, базы данных, UI-блоки и дополнительные методы ранжирования.

## 33. Ограничения подхода

Для корректного научного описания важно указать не только преимущества, но и ограничения.

Система зависит от качества исходных новостей. Если источник публикует неполный, искажённый или нерелевантный текст, downstream-аналитика также может ухудшиться.

Embedding-модели не всегда идеально понимают доменный финансовый контекст. Поэтому используется hybrid retrieval, где semantic search дополняется BM25, фильтрацией и rerank.

LLM может ошибаться в интерпретации. Поэтому её роль ограничена смысловой классификацией и объяснением, а не расчётом объективных численных показателей.

RAG снижает риск галлюцинаций, но не устраняет его полностью. Для этого используются системные ограничения, источники, метаданные и запрет на использование фактов вне контекста.

Локальная Ollama зависит от ресурсов машины. Большие модели могут отвечать медленно, поэтому предусмотрены параметры таймаутов, размера контекста и длины ответа.

## 34. Почему подход подходит для дипломного проекта

Выбранная архитектура демонстрирует полный цикл построения прикладной AI-системы:

```text
сбор данных
    ↓
очистка и нормализация
    ↓
семантическое представление
    ↓
индексация
    ↓
retrieval
    ↓
LLM reasoning
    ↓
объяснимый вывод
    ↓
интеграция в пользовательский интерфейс
```

В проекте используются современные методы обработки текста и retrieval:

- embeddings;
- semantic search;
- BM25;
- FAISS;
- Chroma;
- RAG;
- multi-query retrieval;
- reranking;
- NER;
- локальные LLM;
- streaming-ответы.

При этом система не является демонстрационным чат-ботом “поверх модели”. Она строит собственную базу знаний из новостей, обрабатывает события, формирует аналитические файлы и использует LLM как один из компонентов пайплайна.

Это делает проект практически значимым: пользователь получает не просто список новостей, а инструмент для анализа новостного фона и его связи с рынком.

## 35. Итоговая формулировка подхода

Предложенная система использует гибридную AI-архитектуру для анализа финансово-новостного потока. Классические алгоритмы обеспечивают воспроизводимую обработку данных, поиск, дедупликацию и расчёты. Языковые модели применяются для смысловой интерпретации, классификации и объяснения. RAG связывает модель с актуальной локальной базой знаний, построенной из сырых новостей, обработанных событий и аналитических сводок.

Главная идея подхода:

```text
данные дают факты;
алгоритмы обеспечивают структуру;
LLM объясняет смысл;
RAG связывает ответ с источниками;
пользователь получает проверяемую аналитику.
```

Такое сочетание делает систему более надёжной, прозрачной и пригодной для финансовой аналитики, чем использование одной только языковой модели или одного только классического поиска.
