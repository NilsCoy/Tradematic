# Методология расчётов и формирования аналитического вывода

Данный документ описывает не техническую структуру сервисов, а научно-методологическую логику, лежащую в основе обработки новостей, построения событий, расчёта влияния и формирования ответов AI-чата.

Система решает задачу преобразования неструктурированного новостного потока в структурированный аналитический сигнал, пригодный для интерпретации пользователем и последующего использования в инвестиционном контексте.

## 1. Общая идея метода

Финансовые рынки реагируют не на сами тексты новостей как последовательности слов, а на события, которые эти новости описывают. Поэтому базовая логика системы строится вокруг перехода:

```text
новостной текст → смысловое представление → событие → связь с активом → объяснение
```

Новость рассматривается как наблюдение о внешнем мире. Несколько новостей могут описывать одно и то же экономическое событие с разной степенью детализации, разными формулировками и из разных источников. Поэтому система не ограничивается классификацией отдельных статей, а пытается агрегировать близкие по смыслу материалы.

Основной принцип:

```text
LLM интерпретирует смысл.
Алгоритмы считают сходство, дубликаты, релевантность и численные признаки.
Пользователь получает объяснение, основанное на найденном контексте.
```

## 2. Представление новости как объекта данных

Каждая новость приводится к единому внутреннему виду:

```text
source, title, text, url, chunks, loaded_at, published_at
```

Где:

- `source` — источник публикации;
- `title` — заголовок;
- `text` — основной текст новости;
- `url` — ссылка на оригинал;
- `chunks` — дополнительные текстовые фрагменты, если основной текст неполный;
- `loaded_at` — время загрузки в систему;
- `published_at` — время публикации новости.

С научной точки зрения это этап нормализации наблюдений. Разные сайты имеют разные HTML-структуры, разные поля RSS и разное качество текста. Система приводит их к единой форме, чтобы далее применять одинаковые алгоритмы анализа.

## 3. Фильтрация и очистка текста

Перед анализом выполняется первичная фильтрация:

- проверяется наличие заголовка;
- проверяется наличие содержательного текста;
- отбрасываются слишком короткие материалы;
- отбрасываются технические страницы, справочники и шум;
- выполняется дедупликация по URL и тексту.

Очистка текста нужна для уменьшения информационного шума. В новостных страницах часто встречаются навигационные элементы, рекламные блоки, подписи, служебные фразы, повторяющиеся элементы интерфейса. Если их не удалить, они будут искажать embedding-векторы и ухудшать поиск похожих документов.

## 4. Дедупликация

Дедупликация выполняется на двух уровнях.

Первый уровень — точная дедупликация. Для новости считается хеш:

```text
hash = H(url, normalized_text)
```

Если такая комбинация уже встречалась, новость считается повтором.

Второй уровень — семантическая дедупликация. Даже если URL и формулировки отличаются, две новости могут описывать один и тот же факт. Для этого текст переводится в embedding-вектор, после чего считается косинусная близость:

```text
cosine_similarity(a, b) = (a · b) / (||a|| · ||b||)
```

Если близость выше заданного порога, новость считается смысловым дублем или кандидатом на объединение с уже известным событием.

Косинусная мера используется потому, что для нормализованных embedding-векторов направление вектора важнее абсолютной длины. Это позволяет сравнивать смысл текстов независимо от их размера.

## 5. Embedding-представление текста

Embedding — это числовой вектор, представляющий смысл текста в многомерном пространстве. Близкие по смыслу тексты получают близкие векторы.

Пример:

```text
"ЦБ снизил инфляционный прогноз"
"Банк России обновил ожидания по инфляции"
```

Такие тексты могут иметь разные слова, но их embedding-векторы будут находиться рядом.

В системе используются multilingual-модели, так как новостной поток может включать русский и иностранные источники. Для локального RAG используется embedding-модель Ollama `nomic-embed-text`, а для EDMI-обработки может использоваться multilingual sentence-transformers.

Embedding применяется для:

- поиска похожих новостей;
- группировки материалов в события;
- построения FAISS-индекса;
- Chroma/vector retrieval;
- семантического поиска по вопросу пользователя.

## 6. Агрегация новостей в события

Одна новость не всегда равна одному событию. Несколько публикаций могут описывать один факт:

```text
"Росстат сообщил о снижении инфляции"
"Инфляция в апреле составила 0,14%"
"Экономисты оценили замедление роста цен"
```

Такие материалы должны рассматриваться как единое событие.

Событие является агрегированной смысловой единицей. Оно может содержать:

- основной заголовок;
- список связанных новостей;
- временной диапазон публикаций;
- количество источников;
- embedding-центр;
- извлечённые сущности;
- тип события;
- связь с активами;
- объяснение влияния.

Embedding-центр события может интерпретироваться как среднее смысловое представление группы новостей:

```text
event_vector = mean(news_vector_1, news_vector_2, ..., news_vector_n)
```

Это позволяет сравнивать уже не отдельные статьи, а агрегированные события.

## 7. Извлечение сущностей

После группировки система извлекает именованные сущности:

- компании;
- страны;
- валюты;
- регуляторов;
- отрасли;
- сырьевые товары;
- макроэкономические понятия;
- политические субъекты.

Для русского языка используется Natasha. Смысл этого этапа — перейти от текста к экономически интерпретируемым объектам.

Например, из новости:

```text
Росстат сообщил, что инфляция в апреле снизилась до 0,14%.
```

можно извлечь:

```text
регулятор/организация: Росстат
макроэкономическое понятие: инфляция
показатель: 0,14%
период: апрель
```

Сущности используются как признаки для классификации события и оценки его связи с активами.

## 8. Классификация типа события

LLM используется для смысловой классификации события. На вход ей передаются:

- краткое описание события;
- заголовки связанных новостей;
- извлечённые сущности.

Модель возвращает тип события, например:

```text
macro
regulation
geopolitics
earnings
supply_chain
product_launch
```

Важно: LLM не рассчитывает рыночное влияние. Она только помогает интерпретировать смысл события.

Например, новость про инфляцию относится к классу `macro`, потому что описывает макроэкономический показатель, потенциально влияющий на ставки, стоимость капитала и ожидания инвесторов.

## 9. Связь события с активом

Для каждого актива пользователя система оценивает, насколько событие связано с этим активом.

Уровни связи:

```text
direct       — прямое влияние
industry     — отраслевое влияние
supply_chain — влияние через цепочку поставок
macro        — макроэкономическое влияние
global       — общий рыночный фон
noise        — нерелевантно
```

Пример:

```text
Событие: снижение инфляции
Актив: банковский сектор
Связь: macro / industry
```

Логика: инфляция влияет на ожидания по ключевой ставке, ключевая ставка влияет на стоимость фондирования, кредитную активность, маржу и оценку финансовых компаний.

## 10. Расчёт рыночного влияния

Численное влияние события рассчитывается кодом, а не LLM.

Сначала берётся цена актива до события и после события:

```text
price_before
price_after
```

Затем рассчитывается относительная дельта:

```text
delta = (price_after - price_before) / price_before
```

Далее дельта умножается на вес релевантности:

```text
impact = delta * relevance_weight
```

Веса:

```text
direct       = 1.0
industry     = 0.7
supply_chain = 0.5
macro        = 0.3
global       = 0.2
noise        = 0.0
```

Таким образом система разделяет две задачи:

- LLM определяет смысловую связь;
- алгоритм считает численную оценку влияния.

Это снижает риск галлюцинаций и делает расчёт воспроизводимым.

## 11. Построение RAG-базы знаний

RAG означает Retrieval-Augmented Generation — генерация ответа с предварительным поиском релевантного контекста.

Вместо того чтобы просить LLM отвечать только из параметрической памяти, система сначала ищет документы в собственной базе знаний:

```text
вопрос пользователя
    ↓
поиск релевантных документов
    ↓
формирование контекста
    ↓
LLM генерирует ответ только на основе контекста
```

В базу знаний попадают:

- сырые новости;
- обработанные события;
- RAG-представление событий;
- анализ по активам;
- рыночная сводка;
- память предыдущих ответов.

Это позволяет чату работать не с абстрактными знаниями модели, а с актуальным новостным состоянием системы.

## 12. Chunking

Длинные тексты делятся на фрагменты — chunks.

Причины:

- embedding-модели имеют ограничение на длину входа;
- длинный документ может содержать несколько разных смысловых блоков;
- поиск по небольшим фрагментам точнее, чем по целой статье;
- LLM получает более компактный контекст.

Chunking выполняется с overlap, то есть соседние фрагменты частично пересекаются:

```text
chunk_1: слова 1–180
chunk_2: слова 140–320
chunk_3: слова 280–460
```

Overlap нужен, чтобы важная мысль не потерялась на границе двух чанков.

## 13. Hybrid retrieval

Поиск документов выполняется гибридно. Используются несколько подходов:

```text
BM25 + FAISS + Chroma + keyword score + domain boost
```

Каждый метод решает свою задачу.

### BM25

BM25 — классический вероятностный алгоритм полнотекстового поиска. Он хорошо находит документы, где встречаются важные слова из запроса.

Упрощённо BM25 учитывает:

- сколько раз термин встречается в документе;
- насколько термин редкий в коллекции;
- длину документа.

Если пользователь спрашивает:

```text
Что по инфляции?
```

BM25 хорошо найдёт документы, где явно есть слово `инфляция`.

### FAISS

FAISS используется для векторного поиска. Он ищет документы, embedding которых близок к embedding вопроса.

Это нужно, когда пользователь и документ используют разные слова, но один смысл.

Например:

```text
Запрос: "Что с ростом цен?"
Документ: "Инфляция в апреле снизилась..."
```

BM25 может не увидеть прямого совпадения, а embedding-поиск найдёт смысловую близость.

### Chroma

Chroma также используется как vector store. Он хранит embedding-документы и позволяет выполнять дополнительный семантический поиск.

### Keyword score

Дополнительно считается простая доля совпавших ключевых слов:

```text
keyword_score = matched_query_terms / total_query_terms
```

Это простой, но полезный сигнал для коротких запросов.

### Domain boost

Для финансовой системы важны не все новости одинаково. Поэтому документы получают дополнительный вес, если содержат финансово-экономические маркеры:

```text
курс, ставка, инфляция, прибыль, выручка, санкции, нефть, газ, ЦБ, ФРС
```

Шумные документы, например спорт, кино, развлекательные материалы, получают штраф.

Это нужно, чтобы на вопрос о мировых событиях система не выбирала нерелевантную новость только потому, что она текстово похожа или случайно попала в источник.

## 14. Итоговая формула ранжирования

В текущей логике итоговый score документа является суммой нескольких нормированных сигналов:

```text
score =
    0.35 * BM25_score
  + 0.30 * FAISS_score
  + 0.20 * Chroma_score
  + 0.10 * keyword_score
  + 0.05 * domain_boost
```

Где:

- `BM25_score` — лексическая релевантность;
- `FAISS_score` — семантическая близость;
- `Chroma_score` — дополнительная vector-релевантность;
- `keyword_score` — совпадение ключевых слов;
- `domain_boost` — поправка на финансово-экономическую значимость.

Такой подход называется hybrid retrieval, потому что объединяет лексический и семантический поиск.

## 15. Расшифровка примера ответа retrieval

Пример:

```json
{
  "question": "Что по мировым событиям?",
  "queries": [
    "Что по мировым событиям?",
    "рыночная сводка экономика инфляция ставки нефть газ санкции геополитика",
    "market brief macro economy rates inflation oil gas geopolitics"
  ],
  "matches": [
    {
      "score": 0.30511,
      "doc_id": "546fc263b7e039cb75985e45",
      "chunk_id": "csv2_3_2",
      "title": "Росстат: инфляция в апреле снизилась до 0,14 %",
      "source": "МК Экономика",
      "url": "https://www.mk.ru/economics/2026/05/17/rosstat-inflyaciya-v-aprele-snizilas-do-014-.html",
      "published_at": "2026-05-17T12:45:49+00:00",
      "text": "..."
    }
  ]
}
```

### `question`

Исходный вопрос пользователя.

```text
Что по мировым событиям?
```

Это естественно-языковой запрос. Он может быть неточным и широким, поэтому система расширяет его.

### `queries`

Список поисковых запросов, которые реально используются retrieval-системой.

Первый запрос — исходный:

```text
Что по мировым событиям?
```

Дополнительные запросы добавляются для повышения recall:

```text
рыночная сводка экономика инфляция ставки нефть газ санкции геополитика
market brief macro economy rates inflation oil gas geopolitics
```

Это нужно, потому что пользователь может спросить очень общо, а в документах могут встречаться конкретные термины: инфляция, ставки, нефть, газ, санкции, геополитика.

### `matches`

Список найденных релевантных фрагментов.

Каждый элемент `matches` — это документ или chunk, который система считает полезным для ответа.

### `score`

Числовая оценка релевантности документа вопросу.

Например:

```text
score = 0.30511
```

Это не вероятность и не точность в процентах. Это агрегированный retrieval-рейтинг, рассчитанный как взвешенная сумма нескольких сигналов: BM25, FAISS, Chroma, keyword score и domain boost.

Чем выше `score`, тем выше документ ранжируется относительно других документов в текущем запросе.

### `doc_id`

Идентификатор исходного документа. Он нужен, чтобы понимать, какие chunks относятся к одной статье или одному аналитическому артефакту.

### `chunk_id`

Идентификатор конкретного фрагмента документа.

Например:

```text
csv2_3_2
```

Это означает, что документ был получен из CSV-источника, обработан как часть набора и разбит на несколько чанков. Чат использует именно найденный chunk, а не обязательно весь исходный текст.

### `title`

Заголовок найденного документа.

В примере:

```text
Росстат: инфляция в апреле снизилась до 0,14 %
```

Заголовок помогает LLM и пользователю понять смысл найденного контекста.

### `source`

Источник документа.

В примере:

```text
МК Экономика
```

Источник важен для интерпретации достоверности и происхождения информации.

### `url`

Ссылка на оригинальную публикацию. Она позволяет проверить первоисточник.

### `published_at`

Время публикации. Для финансового анализа это принципиально важно, потому что влияние события на рынок привязано ко времени.

### `text`

Найденный текстовый фрагмент, который передаётся в LLM как контекст.

В примере текст содержит:

- значение инфляции;
- динамику цен;
- прогноз ЦБ;
- прогноз Минэкономразвития;
- оценку экономиста;
- вывод о неустойчивости тренда.

На основе этого LLM может сформировать ответ:

```text
Среди важных мировых/макроэкономических событий выделяется снижение инфляции.
Это может влиять на ожидания по ставкам и рыночные настроения.
Однако тренд пока неустойчив, поэтому вывод требует осторожности.
```

## 16. Формирование финального ответа

После retrieval система формирует prompt для LLM. В него входят:

- вопрос пользователя;
- сгенерированные поисковые запросы;
- найденные документы;
- источники;
- даты публикации;
- память предыдущих ответов;
- вспомогательный анализ тренда.

LLM получает инструкцию:

```text
Отвечать только на основе RAG-контекста.
Не выдумывать факты.
Разделять факт, экономический смысл и возможное влияние.
```

Финальный ответ является не пересказом одной новости, а синтезом найденных документов.

## 17. Роль памяти

Память хранит прошлые события и ответы. Она используется как дополнительный контекст.

Это позволяет системе учитывать историю предыдущих вопросов, но память не является основным доказательством. Основной источник ответа — актуальные документы, найденные retrieval-системой.

## 18. Анализ тренда

В системе есть простой модуль trend analysis. Он извлекает числовые значения из текста и сравнивает первое и последнее найденное число.

Упрощённая логика:

```text
если последнее число > первого → рост
если последнее число < первого → падение
иначе → стабильность
```

Это вспомогательный сигнал, а не полноценная эконометрическая модель. Его задача — дать LLM дополнительную подсказку, если в тексте есть числовая динамика.

## 19. Ограничения метода

Метод имеет несколько ограничений.

Во-первых, качество вывода зависит от качества входных новостей. Если парсер собрал шумные материалы, retrieval может выбрать нерелевантные документы.

Во-вторых, LLM не является источником фактов. Она формирует объяснение на основе найденного контекста. Если контекст неполный, ответ тоже будет неполным.

В-третьих, score в retrieval не является вероятностью истинности. Это только относительная оценка релевантности.

В-четвёртых, простая модель trend analysis не заменяет статистический анализ временных рядов.

В-пятых, impact события зависит от качества рыночных данных и корректности временной привязки новости к цене актива.

## 20. Научная интерпретация

Система сочетает несколько классов методов:

- обработка естественного языка;
- векторное представление текстов;
- информационный поиск;
- кластеризация смысловых наблюдений;
- извлечение именованных сущностей;
- retrieval-augmented generation;
- rule-based scoring;
- событийный анализ;
- интерпретируемое объяснение результата.

С методологической точки зрения это гибридная AI-система. Она не полагается полностью на LLM, а разделяет задачи:

```text
Нейросетевые модели:
    - embedding;
    - смысловая классификация;
    - генерация объяснения.

Детерминированные алгоритмы:
    - дедупликация;
    - BM25;
    - FAISS/Chroma retrieval;
    - расчёт дельты;
    - расчёт impact;
    - фильтрация шума;
    - хранение и воспроизводимость.
```

Такой подход повышает устойчивость системы, потому что наиболее критичные численные расчёты выполняются воспроизводимым кодом, а LLM используется там, где требуется интерпретация естественного языка.

## 21. Итог

Финальный аналитический вывод формируется следующим образом:

```text
1. Пользователь задаёт вопрос.
2. Вопрос расширяется дополнительными поисковыми формулировками.
3. Система ищет релевантные документы через BM25, FAISS и Chroma.
4. Документы ранжируются по hybrid score.
5. Шумные документы штрафуются или отбрасываются.
6. Лучшие chunks передаются в LLM.
7. LLM формирует ответ только на основе найденного контекста.
8. Ответ возвращается пользователю вместе с источниками и внутренними matches.
```

Таким образом, пользователь видит не просто генеративный текст, а объяснение, основанное на конкретных новостях, событиях и аналитических артефактах, собранных системой.
